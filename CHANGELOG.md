  Вы посмотрели всё новое в городе. Награда — повтор лучшего по вашим интересам. Свежие события уже в пути». Одно событие может встретиться в разных кругах (у каждого

## 2026-10-17 · #7 Дедупликация, шаг 2: поиск дубликатов

**Что сделано.** Новый модуль `apps/server/src/modules/dedup/`:
- `dedup.match.ts` — логика сравнения (чистые функции, без БД):
  1. **Блокировка:** сравниваются только события одного города с сеансом в тот же день и **из разных источников**.
  2. **Название:** нормализация (регистр, ё→е, «12+», знаки, служебные слова «концерт», «балет», «спектакль»…,
     слова названия площадки внутри заголовка — с учётом падежей), затем максимум из: доли общих слов,
     вхождения короткого названия в длинное (0.9), сходства по триграммам (устойчиво к падежам).
  3. **Площадка:** по координатам (≤200 м → 1, ≤500 м → 0.6, ≤1 км → 0.2) или по названию; неизвестна → 0.5.
  4. **Время:** ближайшие сеансы ≤15 мин → 1, ≤1 ч → 0.7, ≤3 ч → 0.3.
  5. **Оценка:** `0.5·название + 0.3·площадка + 0.2·время ≥ 0.75` и при этом название ≥ 0.6
     (в одном зале в одно время могут идти разные события).
  6. **Группы:** пары объединяются (union-find); основное событие — самое полное карточкой
     (картинка +3, ссылка на билет +2, цена +1, описание >100 символов +1), при равенстве — добавленное раньше.
- `dedup.service.ts` — `deduplicateEvents()`: берёт активные события с сеансами от «сутки назад»,

  данные, пометка снимается. Возвращает статистику `considered, pairsCompared, duplicatePairs, clusters,

- `parser-sync.plugin.ts` — дедупликация запускается после каждого импорта снимков парсера

## 2026-10-16 · #1 Рандомизированная лента рекомендаций

**Проблема.** Все категории, выбранные в онбординге, получали одинаковые +12 очков,
поэтому события с равным скором шли в порядке добавления в БД — то есть блоками:
сначала всё кино, потом весь стендап и т.д.

**Что сделано.**
- Очки события теперь не задают жёсткий порядок, а увеличивают *шанс* оказаться выше.
  Вес события = `e^(score / 4)`, порядок — взвешенное случайное перемешивание
  (алгоритм Efraimidis–Spirakis). Выбранная категория ≈ в 20 раз «шансовее» невыбранной,
  поведение (лайки, время просмотра, ±8 очков) меняет шанс до ~7 раз.
- События невыбранных категорий тоже изредка попадают в ленту (~8–9% при типичном каталоге) —
  так система может узнать о новых интересах пользователя.
- Не больше 2 событий одной категории подряд (берём ближайшее событие другой категории
  из следующих 10).
- Режим «Рядом» (переданы координаты) не изменён — по-прежнему строго по расстоянию.

**Файлы для замены на сервере:**

- `apps/server/src/modules/feed/feed.routes.ts` — сортировка по скору заменена на
  взвешенное перемешивание + перемешивание категорий (кроме режима «Рядом»).

**Настройка.** Константы в начале нового блока `feed.scoring.ts`:
`FEED_TEMPERATURE` (меньше — очки влияют сильнее, больше — лента случайнее),
`FEED_MAX_SAME_CATEGORY_IN_ROW`.

**Проверено.** Симуляция 1000 лент по 20 событий (3 выбранные категории по 40 событий,
5 прочих по 40): выбранные ≈ 30% каждая, прочие ≈ 1,7% каждая, максимум 2 подряд.
Синтаксис `feed.routes.ts` проверен парсером. Полная проверка типов (`pnpm typecheck:server`)
не выполнялась — запустите на сервере.

**Как проверить на сервере.**
1. `pnpm typecheck:server`
2. Перезапустить API.
3. Открыть ленту пользователем с 2–3 выбранными категориями — категории должны идти вперемешку,
   при обновлении страницы порядок меняется.
